# Объяснение финального проекта: Telco Customer Churn

---

## Что мы делаем и зачем?

**Задача:** бинарная классификация — предсказать, **уйдёт ли клиент** (`Churn = Yes / No`) от телеком-провайдера, основываясь на 20 признаках (демография, услуги, тариф, способ оплаты, длительность контракта).

В реальной жизни такое нужно бизнесу для **удержания клиентов**: предсказали, что клиент скоро уйдёт → отправили скидку / позвонили / предложили апгрейд. Уход одного клиента стоит дороже, чем удержание десяти существующих.

**Главный вызов:** датасет смешанный — числовые признаки (`tenure`, `MonthlyCharges`, `TotalCharges`) соседствуют с категориальными (`Contract`, `PaymentMethod`, `InternetService` и десяток Yes/No-флагов). Классы несбалансированы: только ~26.5% клиентов уходят. Поэтому пайплайн:

```
Сырой CSV
   ↓ Очистка (TotalCharges → float, заполнение пропусков, кодировка Churn)
Чистый DataFrame
   ↓ Визуализация + анализ выбросов
   ↓ Encoding (бинарные → 0/1, многоклассовые → One-Hot)
Матрица 7043 × 23
   ↓ Train/Test split (stratify, 80/20) + StandardScaler
   ↓ Кластеризация (для понимания структуры данных)
   ↓ PCA (≥95% variance)
   ↓ 5 ML-моделей + GridSearchCV (scoring='roc_auc')
   ↓ Простая нейронная сеть (PyTorch MLP)
Лучшая модель + бизнес-выводы
```

## Наши данные: `WA_Fn-UseC_-Telco-Customer-Churn.csv`

- **Источник:** [Kaggle: Telco Customer Churn (IBM Sample Data)](https://www.kaggle.com/datasets/blastchar/telco-customer-churn)
- **Размер:** 7043 строки × 21 столбец (после удаления `customerID` — 20 признаков)
- **Целевой столбец:** `Churn` со значениями `Yes` (1869, 26.5%) / `No` (5174, 73.5%) — **дисбаланс**
- **Признаки:**
  - **Числовые (3):** `tenure` (мес.), `MonthlyCharges`, `TotalCharges`
  - **Бинарные (6):** `gender`, `SeniorCitizen`, `Partner`, `Dependents`, `PhoneService`, `PaperlessBilling`
  - **Многоклассовые (10):** `MultipleLines`, `InternetService`, `OnlineSecurity/Backup/...`, `Contract`, `PaymentMethod`

После One-Hot Encoding → **23 числовых признака**, что укладывается в требование задания «10–20+ features».

## Шаг 1 — Очистка данных

Минимум NaN, но есть **скрытые пропуски**:

1. `customerID` — удаляем (это идентификатор, не признак, иначе модель «выучит ID»).
2. `TotalCharges` хранится как строка. У 11 клиентов с `tenure=0` (новички, ещё не платили) там стоит пробел `" "`. После `pd.to_numeric(errors='coerce')` они становятся NaN → заполняем нулём (логично: суммарные платежи = 0).
3. `Churn` → `0/1`.

**Выбросы.** По IQR в трёх числовых признаках — **ровно 0 выбросов**:
- `tenure ∈ [0, 72]` (диапазон контракта)
- `MonthlyCharges ∈ [18.25, 118.75]` (реальные тарифы)
- `TotalCharges` — производное

**Решение:** выбросы НЕ удаляем — все значения в реалистичных пределах, удаление исказило бы клиентскую базу.

---

## Шаг 2 — Encoding

```
"No internet service" / "No phone service"  →  "No"   (фактически нет услуги)
Yes/No / Male/Female                         →  0 / 1
Contract, PaymentMethod, InternetService     →  pd.get_dummies(drop_first=True)
```

Почему `drop_first=True`? Чтобы избежать **dummy variable trap** — линейной зависимости между one-hot колонками, на которой LogReg ломается из-за мультиколлинеарности.

**Итог:** `(7043, 24)` → 23 признака + Churn.

## Шаг 3 — Визуализация и heatmap

### Распределение классов

Дисбаланс 73.5% / 26.5% — это **критично**. Реакция:
- `stratify=y` при `train_test_split` → пропорции сохраняются в train и test;
- метрика **ROC-AUC** > accuracy (accuracy на дисбалансе врёт: «всегда No» даёт 73.5% точности при нулевой пользе);
- для классических моделей — `class_weight='balanced'` в GridSearch;
- для нейросети — `pos_weight = N_neg / N_pos = 2.77` в `BCEWithLogitsLoss`.

## Шаг 4 — Кластеризация (KMeans / HDBSCAN / Hierarchical)

Зачем кластеризация в задаче классификации? Чтобы понять, **есть ли в данных естественная сегментация** — если да, её можно использовать как фичу или хотя бы интерпретировать клиентскую базу.

| Алгоритм | Результат | Вывод |
|---|---|---|
| **KMeans** (elbow + silhouette на k=2..8) | best k = **4** | Стабильные интерпретируемые группы, линейное время |
| **HDBSCAN** (min_cluster_size=50, сэмпл 2000) | 2 кластера, **1727/2000 точек — шум** | Плотностный подход проваливается — после One-Hot пространство «размазано», нет плотных регионов |
| **Hierarchical** (Ward, сэмпл 500, dendrogram) | ~2–3 естественные группы | O(N²) память — на 7000 точек не масштабируется напрямую |

### Обоснование выбора: KMeans

- **HDBSCAN не подходит** — почти весь датасет он считает шумом, потому что One-Hot Encoding делает евклидово пространство квази-равномерным, без плотных «комков».
- **Hierarchical не масштабируется** на полный датасет, и его сэмпл-результат согласуется с KMeans (≈2–4 группы).
- **KMeans** работает на масштабированном евклидовом пространстве, даёт стабильные центры, линейная сложность.

Визуально кластеры (в PCA-2D проекции) **частично совпадают** с настоящими метками Churn — значит, структура данных уже несёт сигнал об уходе.

## Шаг 5 — PCA для ≥95% variance

```
PCA().fit(X_train_sc)
cumvar = cumsum(explained_variance_ratio_)
n_95 = argmax(cumvar >= 0.95) + 1
```

**Результат:** нужно **18 компонент из 23** для покрытия 95% дисперсии. Сжатие слабое (-22%) — категориальные признаки после One-Hot почти ортогональны друг другу, и PCA мало что может «склеить».

Поэтому для финальных моделей мы **используем полный `X_train_sc` (23 признака)**, а не PCA-версию: 5 «лишних» признаков не дают переобучения на 5634 примерах, а информацию терять не хочется.

## Шаг 6 — Классические ML-модели

5 моделей × `GridSearchCV(scoring='roc_auc', cv=StratifiedKFold(5))`:

| Модель | Лучшие гиперпараметры (CV) | CV ROC-AUC |
|---|---|---|
| LogReg | `C=10, penalty='l2', class_weight=None` | 0.8464 |
| DecisionTree | `max_depth=6, min_samples_leaf=50, class_weight='balanced'` | 0.8315 |
| RandomForest | `n_estimators=200, max_depth=6, min_samples_leaf=1` | 0.8469 |
| AdaBoost | `n_estimators=200, learning_rate=1.0` | 0.8488 |
| **GradientBoost** | `n_estimators=200, max_depth=2, learning_rate=0.05` | **0.8494** |

**Почему `scoring='roc_auc'`?** На дисбалансе классов accuracy ведёт оптимизацию «в ничью» — модель учится говорить «No» большинству. ROC-AUC же измеряет ранжирующую способность, инвариантную к порогу и пропорции классов.

После переобучения на полном train с лучшими параметрами и оценки на 1409 тестовых примерах:

| # | Model | Accuracy | Precision | Recall | F1 | ROC-AUC |
|---|---|---|---|---|---|---|
| 1 | **RandomForest** | **0.79** | **0.67** | **0.43** | **0.53** | **~0.846** |
| 2 | GradientBoost | ~0.79 | ~0.65 | ~0.50 | ~0.56 | ~0.844 |
| 3 | LogReg | ~0.81 | ~0.66 | ~0.55 | ~0.60 | ~0.843 |
| 4 | AdaBoost | ~0.80 | ~0.64 | ~0.50 | ~0.56 | ~0.842 |
| 5 | DecisionTree | ~0.76 | ~0.54 | ~0.74 | ~0.62 | ~0.830 |

> **Лучшая модель на тесте: RandomForest** (по ROC-AUC). Разница между топ-4 моделями — в пределах **0.5 п.п. AUC**, что близко к шуму одного train/test split.

### Confusion matrix лучшей (RandomForest) на тесте

```
              precision    recall  f1-score   support
    No churn       0.82      0.92      0.87      1035
       Churn       0.67      0.43      0.53       374
    accuracy                           0.79      1409
```

Что видно:
- модель хорошо отличает «остающихся» (recall 92%);
- **recall на Churn всего 43%** — модель «пропускает» больше половины уходящих клиентов;
- precision на Churn = 67% — когда говорит «уйдёт», в 2/3 случаев права.

Это классический трейд-офф на дисбалансе. Если бизнесу важнее **поймать всех потенциальных уходов** (recall) — нужно понижать порог решения с 0.5 или использовать `class_weight='balanced'` агрессивнее.

## Шаг 7 — Простая нейронная сеть (PyTorch)

### Архитектура

```
Input(23) → Linear(64) → ReLU → Dropout(0.3)
          → Linear(32) → ReLU → Dropout(0.3)
          → Linear(1)                          ← logits, без Sigmoid
```

Параметров: **3649**.

### Обоснования каждого выбора

| Решение | Почему именно так |
|---|---|
| **2 скрытых слоя 64→32** | Данных немного (5634 train). Глубже → переобучение. Двух слоёв достаточно для нелинейных взаимодействий между tenure × contract × payment |
| **ReLU** на скрытых | Стандарт для табличных MLP: нет vanishing gradient, быстрая. Sigmoid/tanh «насыщаются» и обучают медленнее |
| **Dropout 0.3** | Компромисс: 0.5 (как в CV/ResNet) на табличках переобучается «снизу», <0.2 — почти не регуляризует. 0.3 даёт лучший val_loss |
| **Adam, lr=1e-3, weight_decay=1e-5** | Адаптивные lr по параметрам — работает «из коробки». SGD требовал бы lr-scheduler. weight_decay = слабая L2-регуляризация |
| **`BCEWithLogitsLoss`** (а не Sigmoid + BCE) | Численно стабильнее (log-sum-exp трюк), нативно принимает `pos_weight` для дисбаланса |
| **`pos_weight = 2.77`** (= 4139 / 1495) | Компенсация дисбаланса на уровне функции потерь: ошибка на классе Churn = 1 «весит» в 2.77 раза больше |
| **Early stopping (patience=8 на val_loss)** | Защита от переобучения. Сработал на epoch 15 |
| **batch_size=64** | Маленький бэтч → больше шума в градиентах → лучше регуляризация на маленьких данных |
| **Train/Val split 85/15 внутри train** | Чтобы early stopping смотрел не на тест (избегаем утечки) |

### Результаты на тесте

| Metric | NN |
|---|---|
| Accuracy | **0.7473** |
| Precision | 0.5163 |
| Recall | **0.7620** |
| F1 | 0.6156 |
| ROC-AUC | 0.8396 |

Нейросеть «перекосила» предсказания в пользу класса Churn из-за `pos_weight=2.77`:
- Высокий **recall (76%)** — ловит большинство уходящих;
- Но низкая **precision (52%)** — много ложных тревог.

Это полезный профиль, если бизнесу выгоднее «обзвонить лишних 100 клиентов, чем пропустить 50 уходящих».

| 3 | LogReg | ~0.81 | ~0.66 | ~0.55 | ~0.60 | ~0.843 |
| 4 | AdaBoost | ~0.80 | ~0.64 | ~0.50 | ~0.56 | ~0.842 |

Все ROC-AUC лежат в коридоре **0.83 – 0.85**. Разница порядка 1 п.п. — фактически шум.

### Что лучше для этой задачи?

**Классический ML (бустинги / RandomForest / LogReg).** Причины:

1. **Данных мало** (~5600 в трейне). NN склонна переобучаться на малом объёме — нужны десятки тысяч примеров, чтобы её преимущество раскрылось.
2. **Признаков мало (23) и они «плоские»** — нет естественной иерархии (как у изображений или текста), которую NN могла бы «выучить» через несколько слоёв.
3. **Табличные данные** — это родная территория градиентных бустингов (XGBoost / LightGBM / CatBoost). Они изначально проектировались для этого формата, NN — нет.
4. **Интерпретируемость**: RandomForest и LogReg дают feature importance / коэффициенты — бизнесу можно объяснить, **почему** клиент уйдёт. NN — чёрный ящик.

**Когда стоит выбрать NN на табличке?** Если данных 100k+, или если нужно нативно учить эмбеддинги для категориальных признаков (TabNet, FT-Transformer), или если потом интегрируется в end-to-end pipeline с другими нейросетевыми компонентами.

## Бизнес-интерпретация (главные драйверы оттока)

По корреляциям и важности признаков в RandomForest:

1. **Короткий `tenure`** — новые клиенты уходят чаще. Решение: программы лояльности первых 6 месяцев.
2. **`Contract = Month-to-month`** — самый текучий тариф. Решение: бонусы за переход на 1/2-летний контракт.
3. **`InternetService = Fiber optic`** — дорогой тариф, легче переключиться к конкуренту. Решение: улучшить качество, добавить пакетные скидки.
4. **Отсутствие `OnlineSecurity` / `TechSupport`** — клиенты без доп-услуг менее «привязаны». Решение: продвигать эти сервисы как удержание.
5. **`PaymentMethod = Electronic check`** — маркер «менее привязанного» клиента. Решение: перевод на автосписание (`Bank transfer (automatic)`).

## Главные ограничения

### 1. Один train/test split

Разница между моделями (~1 п.п. AUC) **меньше дисперсии сплита**. Корректный выбор лучшей модели требовал бы повторного CV на нескольких сидах.

### 2. Дисбаланс не решён полностью

Recall на Churn у RF = 43% — почти половина уходящих не отлавливается. На реальном продакшене лучше:
- понижать decision threshold (например, до 0.3);
- или использовать SMOTE/ADASYN для генерации синтетических примеров класса Churn;
- или калибровать вероятности (`CalibratedClassifierCV`) и принимать решения по ожидаемой стоимости.

### 3. Без feature engineering

Не делали ratio-фичи (`MonthlyCharges / tenure`, `TotalCharges / MonthlyCharges`), не разбивали `tenure` на бакеты (`new/medium/loyal`). Для бустингов это обычно даёт +1–2 п.п. AUC.

### 4. PCA не помог

Сжатие 23 → 18 компонент почти без выигрыша. После One-Hot признаки слишком ортогональны для линейного декорреляционного метода.

## Как улучшить

- **XGBoost / LightGBM / CatBoost** вместо `GradientBoostingClassifier` — те же бустинги, но в 5–10 раз быстрее и обычно +1–2 п.п. AUC из коробки.
- **Threshold tuning** — оптимизировать порог по F1 или по бизнес-метрике (стоимость FP vs FN), а не оставлять 0.5.
- **Feature engineering** — `tenure_bucket`, `charges_per_month`, взаимодействия `Contract × InternetService`.
- **SHAP** для объяснения предсказаний RandomForest — поможет аналитикам.
- **Стэкинг** топ-3 моделей (LogReg + RF + GBM) через `StackingClassifier` — обычно даёт +0.5–1 п.п. AUC бесплатно.
- **Калибровка вероятностей** — RF и бустинги выдают «сжатые» вероятности; `CalibratedClassifierCV(method='isotonic')` их выпрямляет.
